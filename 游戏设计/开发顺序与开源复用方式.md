# 下课之前开发顺序与开源复用方式

开发从一套能启动、能单人进入、能主机建房和加入的开源工程开始。先把校园模型与一个普通角色接进去，验证正常行走。再接齐首版人物和动作，接入丧尸算法，最后把教室开局、楼梯折返、躲避与两条撤离路线组合成一局游戏。

玩法和角色规则见[玩法方案](../下课之前_玩法方案.md)。感知、寻路、转化和联机判定见[丧尸算法](丧尸算法.md)。当前交付是开发方案。下面的运行和验收项目留到开发时执行。

## 先选主工程

**首选整套试跑 OpenFire。** 核对版本为 [7259140](https://github.com/rokasjasonas/openfire/tree/7259140487946532af8310723392cca34a4fb0bb)，上游使用 Godot 4.6、GDScript 和 ENet。工程提供第一人称控制、设置、单人本机开局、局域网或直连 IP 房间、角色生成、主机运行的机器人、合作任务与 Windows 导出配置。以它作为候选主工程的理由是这些模块本来就在一起，并且合作任务可以指定 Godot 地图场景。先用上游对应的 Godot 小版本跑通，随后固定版本。代码采用 MIT，上游美术授权见其许可与素材清单。 [项目说明](https://github.com/rokasjasonas/openfire/tree/7259140487946532af8310723392cca34a4fb0bb) · [许可证](https://github.com/rokasjasonas/openfire/blob/7259140487946532af8310723392cca34a4fb0bb/LICENSE)

OpenFire 原地图由脚本生成并在运行时烘焙导航。校园版需要一个地图接入层，把导入的 GLB、出生点、触发区和分区导航接到主工程的关卡入口。上游玩家节点由所属端控制，原有受伤流程也由受伤者的节点负责。保留现有移动同步作为起点，校园的门、道具、咬击、感染、指挥与撤离结果交给主机判定。 [上游架构](https://github.com/rokasjasonas/openfire/blob/7259140487946532af8310723392cca34a4fb0bb/docs/architecture.md) · [地图基类](https://github.com/rokasjasonas/openfire/blob/7259140487946532af8310723392cca34a4fb0bb/scripts/world/map_base.gd)

如果 OpenFire 的原版单人或双端联机跑不通，或接入校园小场景需要重写大量底座，再试 [TheDahoom FPS Multiplayer Template](https://github.com/TheDahoom/FPS-Multiplayer-Template) 的房间、菜单和第一人称控制，另接任务结算。Zombie Zone 作为丧尸行为来源备选。它自带合作撤离，但地图格式和校园 GLB 接入方式不同，上游也将多层楼梯地图列为待补项。 [Zombie Zone](https://github.com/zees-games/game-zombie-zone)

## 开源复用方式

1. **先复用主工程里已有的功能。** 菜单、房间、玩家同步和关卡入口跟随同一个主工程。先在保留的上游示例地图验证，再逐项换成校园内容。
2. **需要额外功能时搬完整的小模块。** 例如要搬可锁门，就先单独导入门场景、交互脚本和必需资源。查清输入、节点引用、碰撞层、自动加载项和网络权限，再用项目自己的接口接上。每项复用完成后单独验证。
3. **动作直接用现成动画。** 将动作包导入统一的人形骨架，把动画片段映射为本项目的走路、静步、跑步、眩晕或咬击等动作。玩法和动画分别接入。比如播放咬击动画时，由主机在命中时点结算；只替换动作片段时，咬击规则无需随之改写。
4. **找不到合适的部分才交给 AI 补写。** 先尝试调整参数、复用同类片段，再评估搬入模块的成本。没有合适来源时，只写缺的规则和接线。动作缺口先用同类动作、播放速度或简单混合占位，试玩确认确实需要后再补。
5. **记录复用来源。** 每项记录仓库或资产包、版本或提交、取用文件、授权、改动和运行验证。代码、模型、动画和音效分别核对随附许可，摘取 MIT 代码时保留版权和许可证原文。

| 功能 | 先从哪里取 | 校园版要接什么 |
| --- | --- | --- |
| 房间和游戏框架 | OpenFire 的菜单、ENet 建房与加入、世界加载、玩家生成与同步、合作任务运行器 | 单人和最多四人共用校园关卡。先确认本机和两端联机，保留同一种任务入口。 |
| 普通人物移动 | [OpenFire 玩家控制脚本](https://github.com/rokasjasonas/openfire/blob/7259140487946532af8310723392cca34a4fb0bb/scripts/player/player.gd)的移动、视角、蹲伏、冲刺与第三人称表现 | 在已有移动控制上加静步速度与脚步声规则。高瘦在同一个控制器上调冲刺能力。 |
| 门、拾取与投掷 | 先检查主工程现有拾取与投掷流程。可锁门和物品交互参考 [COGITO 官方说明](https://cogito.readthedocs.io/en/latest/about.html)，优先试搬必要场景与组件 | 门状态同时影响碰撞、导航与声音。书本使用投掷组件，落地时发出可供丧尸调查的声音事件。 |
| 人物模型与移动动作 | [Quaternius Zombie Apocalypse Kit](https://quaternius.com/packs/zombieapocalypsekit.html) 的 CC0 带骨架人物，以及 [Universal Animation Library](https://quaternius.com/packs/universalanimationlibrary.html) | 先用带骨架的人物占位。按[角色设定图](校服人物与感染形态_第1版.png)换校服、发型和配件，首版五种形象沿用统一骨架映射。 |
| 丧尸移动、受击及近身动作 | 同一套 Quaternius 人形骨架。优先试 [Universal Animation Library 2](https://quaternius.com/packs/universalanimationlibrary2.html) 与丧尸包中实际可用的片段。Zombie Zone 的[动画层](https://github.com/zees-games/game-zombie-zone/blob/19e65c404db70a318c698a2ae419ae9d426921e1/npcs/zz_zombie_view.gd)可参考如何在走路上叠加垂肩与拖步 | 通过动画片段和混合做蹒跚、眩晕、短距离起手与指挥动作。若没有专用咬击或拍门片段，先用近身和挥手动作代替，在项目里定义时点。 |
| 丧尸感知与寻路 | 先用 OpenFire 已有的视线与导航骨架。再核对 Zombie Zone 的[普通丧尸状态](https://github.com/zees-games/game-zombie-zone/blob/19e65c404db70a318c698a2ae419ae9d426921e1/npcs/zz_common_brain.gd)和 Murder Floor 的[路径跟随状态](https://github.com/cesko/godot_fps_test/blob/bffb9940f1bd4a962d2cc8181719f7a3c65e2b31/scenes/characters/zombie_state_machine/moving.gd) | 接入本项目的脚步、声源记忆、门口聚散和僵尸王指挥。导航沿用 Godot NavMesh 与 A*。可独立复用的逻辑优先搬，强依赖彼此不同的导航框架时只保留主工程的一套。 |
| 校园专有规则 | 先查上游任务、互动、冷却和 NPC 提示接口 | 高壮和高瘦互斥抽选、AI同学分派开路或断后、胶布耐久、感染后切阵营、双出口结算。现成组件负责通用能力，缺的规则由 AI 按玩法方案补写。 |

骨骼导入时先在一个普通角色上配置 Godot 的 `BoneMap` 与 `SkeletonProfileHumanoid`。走路和跑步优先使用原地动作，由已有控制器推进角色。逐个检查脚底、朝向、膝肘弯曲及速度与步幅是否一致，再扩到其他人。动作下载前核对免费包实际包含的片段。 [Godot 骨骼重定向](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html)

## 开发顺序与每一步的验收

### 1 复制主工程并跑通原版

把 OpenFire 固定在验证的提交，保留上游来源。用原版示例地图跑一次单人，再开两个进程做主机和客户端，互相看见对方移动，检查退回菜单和再开一局。对照项目自带的 smoke 与 LAN 场景。确认可启动且可导出 Windows 版之后，建立校园关卡入口。首轮网络验收以本机双进程和局域网为主。

**通过条件**　进房、生成角色、同步、退房和重开都有一条可以重复运行的路径。

### 2 导入校园首段并建立关卡场景

从[校园地面细化母版](../还原/成果/地面补铺与预览优化/校园_地面细化.blend)导出首段 GLB。先导两间教室、一段走廊和一个楼梯口，再接楼外路线。保持模型原有米制和全校统一原点。校园场景引用导入模型，碰撞、门状态、出生与触发点放在 Godot 的外层场景，日后可以按区域更新模型。开局教室楼层和另一处楼梯的连接按[门位与动线核对](../还原/实景门位与游戏动线核对.md)落位。 [Godot GLB 导入](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)

**通过条件**　从主菜单加载校园场景，光照、贴图、方向、大小和出生位置可检查，教室、走廊和楼梯摆在同一套坐标里。

### 3 验证一个普通角色能正常移动

保留开源控制器，先挂一个普通人物的骨架和动作。检查第一人称视角、走路、静步、跑步、蹲下和转身，实走教室门槛、转角与第一段楼梯。用简单碰撞体修复穿墙、掉落和卡台阶。在开发显示里核对静步无脚步事件、走路事件强度正常、跑步更响。再用双端确认对方的移动和姿势表现。

**通过条件**　同一个普通角色能从教室往返楼梯平台，在单人和联机环境下都可辨认动作，无穿墙和明显卡顿。

### 4 接齐首版人物和各自行为

接入普通同学、高壮、高瘦和带路的 AI 同学。普通丧尸与僵尸王使用同一批人物对应的感染外观。各角色复用已经验收的移动和人形骨架，外观、动作和角色能力用独立配置。先在人物测试场通过手动指令触发动作，由测试哑目标或指定点接收结果。

- 普通同学能移动、蹲下、拾取、扔书和关门。
- 高壮能触发短时眩晕动作，高瘦能按配置冲刺。每局在两种能力中随机分配一种。
- AI同学能走到指定点、停留并发出提示。
- 普通丧尸能播放游荡、追击、拍门、咬击、眩晕和散去的动作。僵尸王可控，能发出指挥动作，转化前后外观能对上。

**通过条件**　所有人物能进入场景，动作可触发、可中断、能恢复。指令与动画验证完成后，再让丧尸自主决策。

### 5 接入丧尸算法和主机裁决

按[丧尸算法](丧尸算法.md)把测试指令换成实际事件。先让一只丧尸收到脚步或视线信息，走导航网格到可达点。然后接失去视线后的搜索、关门断路、门外候位和尸群散去。最后接僵尸王派出两三只丧尸、咬击判定、胶布消耗及感染转化。按「状态决定目标，导航决定路线，动画显示动作，主机决定结果」连接模块。

**通过条件**　分别实测静步与跑步、扔书、锁门、两层楼导航和僵尸王标记。两端看到同一扇门、同一批人转化，咬击和胶布消耗各结算一次。

### 6 把模块串成完整关卡

沿用 OpenFire 的合作任务入口和目标提示，配置课程开局、躲避、主楼梯折返、换路下楼、出楼和撤离。原版 `reach_zone` 等待所有存活玩家进入同一指定区。校园关卡接两个出口，每名幸存者抵达任一出口时单独结算，并处理感染离校、转化后继续对局和全队结束。教学提示由 AI 同学根据声响和队友位置发出，联机时可建议高壮开路或断后、高瘦探路或引开丧尸。 [上游合作任务格式](https://github.com/rokasjasonas/openfire/blob/7259140487946532af8310723392cca34a4fb0bb/docs/missions.md)

**通过条件**　Windows 包可从菜单开始一局，单人和双端均可从开局走到结算。分别试正门、西门、躲门、感染转化、队友先离开和重开。最后再扩大校园加载范围、调性能和替换占位资源。
